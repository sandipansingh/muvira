# Isolated integration and hosting verification

Run `pnpm run build`, then `pnpm run test:integration` with `SUPABASE_TEST_URL`, `SUPABASE_TEST_ANON_KEY`, `SUPABASE_TEST_SERVICE_ROLE_KEY` from a freshly reset local Supabase and `SUPABASE_TEST_ISOLATED_LOCAL=true`. The command fails without all configuration or when the URL is not loopback HTTP. The acknowledgement asserts that this local instance contains disposable test data; do not forward a production database onto that port. All twelve database suites run serially to avoid shared lease/order cleanup races. Normal `pnpm test` retains optional DB skips for offline unit work; CI's mandatory integration step cannot silently skip missing configuration.

CI runs database security, API, fencing, provider operation, refund, cancellation, retained checkout, shipping, cart transfer, refund worker, reporting and catalog media suites. These use fixture provider behavior. `pnpm run test:upgrade` uses the same isolated configuration, resets the local database to 048, checks every intermediate contract through 052, preserves existing monetary/provider snapshots, and runs API/cart/recovery suites with the compatibility release profile. CI separately checks clean replay and upgrade from 025. The manually dispatched staging-provider-smoke workflow requires both infrastructure and commerce readiness and checks provider credentials; it is not proof of a real capture, refund, shipping cancellation, or webhook replay journey.

`node --test tests/hosting.test.cjs` checks static startup independent of working directory, SPA HTML navigation, real asset 404s, missing build failure, runner refusal, and deployment redirect configuration. Mounted Playwright suites exercise real cart, checkout, product, refund, fulfillment, catalog and diagnostics components with isolated API/Auth/provider fixtures. The API integration suite separately uses real local Supabase customer/admin identities. These are complementary checks, not a claim of live-provider acceptance. Never start development workers with production credentials. Existing responsive tests are layout audits and do not establish checkout/payment behavior.

## Release profiles

`SCHEMA_RELEASE_MODE=final` is the default and requires structural contract 052. `SCHEMA_RELEASE_MODE=compatibility` accepts only known contracts 048–052; features needing later tables/functions return an explicit upgrade error. Legacy watch inspection continues before 051; persisted due-time scheduling starts at 051. Dashboard aggregation requires 052. Commerce readiness remains separate from infrastructure readiness, so incomplete shipping/pickup configuration stays visible to administrators.

For a compatibility image, build `server/Dockerfile` with `--build-arg SCHEMA_RELEASE_MODE=compatibility` and retain its immutable image digest. The final image defaults to `final`. Compose supplies its own `SCHEMA_RELEASE_MODE` environment value, so set the compatibility profile there explicitly when using that image. A future rollout must deploy the compatibility API before additive migrations and the final client only after 052. Roll back application code using the compatible image without reversing schema additions or provider operations.

## Deployment gates requiring infrastructure access

Deployment was explicitly removed from this implementation's scope by the user on 2026-10-26. Provider behavior was verified with isolated fixtures. The steps below are future release gates; no production migration, DNS change, deployment, live-provider acceptance transaction or 24-hour production monitoring was performed.

The checked-in nginx config returns HTTP 308 for `www.muvira.in`, preserving `$request_uri` (path and query). Dokploy must route BOTH apex and www to this client and provision valid TLS certificates for both hosts. Verify externally with `curl -I 'https://www.muvira.in/products/example?source=check'`: expected Location is `https://muvira.in/products/example?source=check`. Verify apex deep links, missing JS/CSS 404 responses, and the API readiness endpoint after rollout. DNS, ingress routing, TLS and live redirects have not been verified by repository checks.

Repository config review: Compose requires `ALLOWED_ORIGINS` and client build argument `VITE_AUTH_REDIRECT_URL`; neither has a production default. Set production CORS to `https://muvira.in` and auth redirects to the actual canonical apex password-reset URLs used by the app. Supabase `config.toml` intentionally configures localhost for local Auth only; separately inspect hosted Supabase Site URL and allowed redirect URLs. Do not replace local config with production URLs. `.env.example` currently uses placeholder hosts, so it cannot establish deployed canonical configuration. No hosted configuration was inspected or changed.
