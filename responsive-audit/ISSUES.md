# Responsive storefront audit — before fixes

Date: 24 September 2026. The client is Vite 8, React 19, React Router 7, TypeScript, Tailwind CSS 3, and the shared CSS tokens/utilities in `client/src/index.css`. No storefront code was changed during this phase.

## Coverage and evidence

`responsive-audit/audit.mjs` captured 700 full-page screenshots: 20 route entries across 35 viewport/DPR/text-scale cases. These include every requested phone size and orientation, tablet orientation, desktop size, effective zoom width, a 320 CSS px desktop reflow case, DPR 1/1.5/2/3 at 390×844, and simulated 200% browser text sizing at 320×568, 960×540, and 1280×720. It also captured 21 open-menu, drawer, filter, quick-view, search, and password-modal cases. Findings and screenshots are in `before/` (`findings.json`, `overlay-findings.json`). A successful GET response is reused across viewports to avoid the API's 300-request development rate limit; the final matrix recorded ten distinct cached GET responses, all HTTP 200. The initial uncached pass was discarded after it reached HTTP 429.

Checks cover document horizontal overflow, visible descendants outside the viewport, touch targets below 44×44 CSS px, body-copy elements below 14px, fixed/sticky intersections, possible image dimension/resolution risks, vertically clipped controls, and console messages. The dimension and intersection checks are screening heuristics; an image in a fixed-height wrapper can be flagged despite reserved space, and a backdrop can intentionally intersect its dialog. OS-level large-text settings and actual browser zoom are not exposed by this Chromium run; the root-font-size and effective-CSS-viewport cases approximate their layout effects. The open overlays were sampled at 320, 390, 960, and 1280 CSS px.

At normal text size, none of the 640 route/viewport cases had document-level horizontal overflow. At simulated 200% text size, 19 of 60 cases overflowed. The touch checker recorded 7,013 small-target samples across 400 touch cases (capped at 60 samples per case). The body-copy check recorded 1,143 samples below 14px across 635 cases. Image checks recorded 1,806 dimension/aspect-ratio samples and 101 potential DPR sharpness samples; some are repeat sightings of the same shared image. No default-state fixed/sticky overlap or clipped interactive content was detected. There were no app console errors after the cache correction; Chromium logs `Unrecognized feature: 'web-share'` from the Razorpay SDK on each navigation.

## Critical

1. **Search is unreachable at 320px.** Playwright cannot click the visible header Search button: the centered `Muvira` logo intercepts its pointer events. The absolute, centered logo and the right-hand icon group compete for the same space in `client/src/components/layout/Header.tsx:42-82`. Evidence: `before/overlay-findings.json` (`header-search-open`, 320×568); compare [320px header](before/home__320x568-phone-dpr3.jpg) with the [390px open search](before/header-search-open__390x844-phone-dpr3.jpg).
2. **200% text sizing breaks reflow and hides content horizontally.** At 320 CSS px the document reaches 380–583px wide on home, shop, categories, search, PDP, cart, and 404. At 960/1280 CSS px the listing controls extend as far as 1,294/1,522px. The shared container gutters grow with the root font size without enough remaining content width; the fixed centered header arrangement and unshrinkable listing controls/grid tracks amplify it. Causes: `client/src/index.css:374-410`, `client/src/components/layout/Header.tsx:42-82`, `client/src/components/catalog/CatalogTopBar.tsx:50-114`, `client/src/pages/ShopPage.tsx:189-209`, and the parallel layout in `client/src/pages/SearchPage.tsx:246`. Evidence: [320px home at 200% text](before/home__320x568-text-200-dpr1-text200.jpg), [960px shop at 200% text](before/shop__960x540-text-200-dpr1-text200.jpg).

## Major

1. **Touch controls are systematically undersized.** Shared `Button` sizes are 28–40px (`client/src/components/ui/Button.tsx:20-30`). The header icons are 40px (`Header.tsx:82-159`), hero arrows 32–36px (`client/src/components/home/HeroSlider.tsx:144-159`), listing Filter/sort controls about 30px (`CatalogTopBar.tsx:58-104`), product-card actions 36×40px (`client/src/components/catalog/ProductCard.tsx:218-237`), and PDP quantity/gallery controls 28–36px (`client/src/components/product/ProductInfo.tsx:101-126`, `ImageGallery.tsx:101-122`). Small inline links also have no 44px hit area. The audit measured this on every touch case.
2. **Product-card actions rely on hover above the phone breakpoint.** The add-to-cart and quick-view buttons are `opacity-0` until `group-hover` at `sm` and above, while the permanently visible buttons are `sm:hidden` (`client/src/components/catalog/ProductCard.tsx:195-237`). Touch tablets can therefore have invisible actions. The PDP zoom uses only mouse enter/move/leave; there is no touch or pointer zoom/swipe handler (`client/src/components/product/ImageGallery.tsx:39-75`, `ImageGallery.tsx:82-144`).
3. **PDP purchase controls are not persistent on phones.** Add to Cart and Buy Now sit in the scrolling product-info column, with no mobile bottom bar (`client/src/components/product/ProductInfo.tsx:95-151`, `client/src/pages/ProductDetailPage.tsx:164-181`). Long product descriptions and reviews push them far from later content. The gallery offers small arrows and thumbnails but no swipe gesture or tap zoom. Evidence: [320px PDP](before/product__320x568-phone-dpr3.jpg).
4. **Mobile drawers do not manage focus or page scroll.** `MobileMenu` returns a dialog and backdrop without focus trapping or scroll locking (`client/src/components/layout/MobileMenu.tsx:36-60`); `CartDrawer` has the same problem (`client/src/components/cart/CartDrawer.tsx:30-44`), and the mobile filter panel has no trap/lock and leaves its Apply/Reset actions at the end of a scrolling column (`client/src/components/catalog/CatalogSidebar.tsx:263-307`). The shared `Modal` locks body scroll but has no focus trap (`client/src/components/common/Modal.tsx:13-70`). This affects keyboard navigation and short mobile screens. Evidence: [320px filters](before/filters-open__320x568-phone-dpr3.jpg), [320px cart drawer](before/cart-drawer-open__320x568-phone-dpr3.jpg).
5. **Body and helper text is too small.** The audit found 11–12px text in auth explanations/disclaimers (`client/src/pages/SignInPage.tsx`, `client/src/pages/SignUpPage.tsx`), category copy (`client/src/pages/CategoriesPage.tsx`), and footer copyright (`client/src/components/layout/Footer.tsx:110-115`). Much other mobile body copy is `text-sm` (14px), below the requested 16px minimum; examples include PDP description (`ProductInfo.tsx:75-78`) and footer description (`Footer.tsx:23-25`).
6. **Images lack responsive sources and many lack intrinsic dimensions.** There are no `srcSet`/`sizes` attributes in storefront image markup. The audit repeatedly flags `/logo.png`, category art, and banner images without width/height or aspect ratio (`client/src/components/layout/Header.tsx:57-62`, `Footer.tsx:19-22`, `client/src/components/home/CategoryGrid.tsx:65-74`, `client/src/components/home/HeroSlider.tsx:128-140`, `client/src/components/catalog/ShopHero.tsx:24-33`). Fixed-height hero wrappers do reserve space, so their dimension flags need review; logos and some category images remain layout-shift candidates. At larger widths/high DPR, the 1600×900 shop banner and some product images may be upscaled (101 sampled resolution flags). The LCP/CLS/INP targets are not yet measured.
7. **Checkout and account layouts need authenticated verification.** `AuthGuard` redirected every checkout, order, confirmation, failure, and profile visit to sign-in (`client/src/components/auth/AuthGuard.tsx:24-41`). The empty-cart state likewise does not exercise `FlowItemCard`, checkout address/payment, or order details. Static inspection shows the checkout order summary remains a full section on mobile and lacks the requested collapsible summary/sticky action (`client/src/pages/CheckoutPage.tsx:262-430`, `client/src/components/checkout/FlowCartSidebar.tsx:53-200`). This is a coverage gap; it is not evidence of a measured checkout overflow. A local test session and representative cart/order data are needed before declaring those pages responsive.

## Minor

1. `100vh`/`min-h-screen` is used by the layout and auth pages without a `100dvh` override; fixed drawers/bars have no `env(safe-area-inset-*)` padding (`client/src/App.tsx:65-85`, `client/src/pages/SignInPage.tsx:35`, `client/src/pages/SignUpPage.tsx:37`, `client/src/components/layout/MobileMenu.tsx:45-59`, `client/src/components/cart/CartDrawer.tsx:32-43`). Notched phones and mobile browser bars need device verification.
2. The toast stack uses `z-[99999]`, a fixed 380px width, and small dismiss controls (`client/src/components/common/Toast.tsx:48-122`). It could sit above modal/checkout actions; a visible-toast interaction has not yet been measured.
3. Chromium reports only the third-party Razorpay SDK warning `Unrecognized feature: 'web-share'`. No application console error appeared in the corrected audit. The viewport meta tag is present and does not disable zoom (`client/index.html:10`).

## Next audit input

The protected routes, populated cart, live Razorpay handoff, toast stack, long customer names/addresses, and OS-native large text still require representative test states. Phase 2 should retain this distinction and fix the measured storefront failures first; Phase 3 must capture the missing states before claiming complete coverage.
