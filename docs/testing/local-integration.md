# Isolated integration and hosting verification

Run `pnpm run build`, then `pnpm run test:integration` with `SUPABASE_TEST_URL`, `SUPABASE_TEST_ANON_KEY`, `SUPABASE_TEST_SERVICE_ROLE_KEY` from a freshly reset local Supabase and `SUPABASE_TEST_ISOLATED_LOCAL=true`. The command fails without all configuration or when the URL is not loopback HTTP. The acknowledgement asserts that this local instance contains disposable test data; do not forward a production database onto that port. All database suites run serially to avoid shared lease/order cleanup races. Normal `pnpm test` retains optional DB skips for offline unit work; CI's mandatory integration step cannot silently skip missing configuration.

CI runs payment integrity, database security, API, fencing, provider operation, refund, cancellation, retained checkout, custom checkout, shipping, durable shipping, cart transfer, refund worker, reporting, revenue analytics and catalog media suites. These use fixture provider behavior. `pnpm run test:upgrade` uses the same isolated configuration, resets the local database to 048, checks every intermediate contract through 060, preserves existing monetary/provider snapshots, and runs API/cart/recovery suites with the compatibility release profile. At 060 the analytics, retained checkout and fencing suites run again. Upgrade snapshots compare existing money, provider identities and operation state; new refund operations use persisted replay protection, while older dispatched operations remain unprotected and require reconciliation. Retained checkout tests drop real successful expiry RPC responses and verify replay preserves released stock, coupon reservations and the single notification outbox event; captured payments keep committed reservations and reject stale leases. CI separately checks clean replay and upgrade from 025. The manually dispatched staging-provider-smoke workflow requires both infrastructure and commerce readiness and checks provider credentials; it is not proof of a real capture, refund, shipping cancellation, or webhook replay journey.

`node --test tests/hosting.test.cjs` checks static startup independent of working directory, SPA HTML navigation, real asset 404s, missing build failure, runner refusal, and deployment redirect configuration. Mounted Playwright suites exercise real cart, checkout, product, refund, fulfillment, catalog and diagnostics components with isolated API/Auth/provider fixtures. The API integration suite separately uses real local Supabase customer/admin identities. These are complementary checks, not a claim of live-provider acceptance. Never start development workers with production credentials. Existing responsive tests are layout audits and do not establish checkout/payment behavior.

## Release profiles

`SCHEMA_RELEASE_MODE=final` is the default and requires structural contract 060. `SCHEMA_RELEASE_MODE=compatibility` accepts known contracts 048–060 for upgrade inspection. Deploy this payment runtime only after 059 and 060: the new checkout, refund and webhook entry points require those migrations. Compatibility readiness alone does not certify payment API compatibility with earlier schemas. Historical application images remain the rollback option; migrations are append-only.

Retain immutable historical application images for rollback. Apply migrations 059 and 060 before deploying this payment runtime, verify schema contract 060, then check owned checkout recovery, captured finalization, webhook recovery and refund reconciliation on the exact deployed revision. Never reverse financial migrations or provider operations during an application rollback. The earlier [revenue rollout procedure](../operations/admin-revenue-rollout.md) remains historical analytics guidance, not the deployment order for this payment change.

## Payment environment and provider acceptance

Development and Razorpay Test Mode require isolated loopback Supabase. The client and API development environment files must point to that same local Auth/database instance. Inherited process variables take precedence over dotenv files; startup reports inherited field names and a public-key configuration fingerprint without logging values. Set `RAZORPAY_MODE=test` or `live` explicitly; key prefixes must agree. Live Mode requires the production runtime and a non-loopback production database. Outbound notification and fulfillment paths also validate the stored order binding against the current mode and key, so changing process configuration cannot promote a test capture into a real shipment or email. Test Mode blocks outbound shipment mutations and customer email delivery. Payment/refund recovery remains available against the isolated database.

The authenticated payment configuration disables intent and QR in Test Mode. In production, set `RAZORPAY_UPI_INTENT_ENABLED` and/or `RAZORPAY_UPI_QR_ENABLED` only after account capability checks. Desktop QR uses redirect by default. `RAZORPAY_UPI_EMBEDDED_QR_APPROVED=true` records explicit approval for embedded desktop QR. Collect has no control or API path. See Razorpay's [Custom Checkout methods](https://razorpay.com/docs/payments/payment-gateway/web-integration/custom/payment-methods/) and [idempotent refund API](https://razorpay.com/docs/api/refunds/normal-refunds-idempotent/).

Migrations 059–060 preserve historical money and provider references. New order bindings are immutable to the service role and are created transactionally with preparation. Existing unbound records stay in review; do not infer their mode/key from the currently configured credentials. Continue an owned unpaid order through its original request UUID. A definitive provider rejection can reuse that preparation, while a transport timeout or lost attachment requires provider reconciliation. The browser uses a 30-second request deadline and retains the same UUID. Provider calls abort after 20 seconds and never retry order creation automatically.

Verified webhook ingress atomically stores a sanitized receipt and retry job before acknowledging it. The retry scheduler also sweeps unfinished receipts, including expired processing leases. Monitor `aged_razorpay_webhooks`, `aged_checkout_preparations`, reconciliation cases, provider operations and outbox failures. Refund dispatch persists protection before sending `X-Refund-Idempotency`; replay uses the same immutable body and key. Legacy uncertain dispatches without that protection must be reconciled before further action.

Automated provider fixtures, local database transactions and Chromium/WebKit checks are separate from genuine Razorpay acceptance. Supported Test Mode card/bank/wallet completion requires the provider account, approved domain and an isolated test user. Intent/QR completion cannot be certified without Live Mode and remains outside the no-live-testing constraint. Public webhook delivery additionally requires an approved isolated staging endpoint. Do not switch to live credentials to pass a sandbox test.
